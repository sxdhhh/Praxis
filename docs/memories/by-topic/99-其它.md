## 待办 16：PK 403 → 400 的可判别化与频控退避（commit `48df686`）

### 问题
Retrofit 非 2xx 抛 `HttpException`，`message` = `HTTP 403 Client Error`，**响应体被丢弃**。
而 PK 最关键的判据只在 body 里（真机实测）：
| 码 | body | 真因 |
|---|---|---|
| 403 | `{"status":403,"message":"error"}` | 提交接口**独立频控**（窗口约 10 分钟级） |
| 400 | `{"status":400,"message":"请求过于频繁"}` | 出题接口频控 |
旧实现把 403 当普通失败 → `retryBaseMs << n`（800ms/1.6s/3.2s）重试 → **三回合全在窗口内**，白打且推长窗口（真机日志那串 `match → 400 请求过于频繁` 就是这么来的）。

### 修法
1. 新增 `core/pk/PkHttpException.kt`：带 `code` + `body`，`isRateLimited` 判定（429 / 403 / body 含「频繁」「too many」「rate limit」）。
2. `PkBattleRepository.fetchMatch/submit` 捕获 `retrofit2.HttpException` → 转 `PkHttpException`（读 `response().errorBody().string()`），并 `AppLogger.w("PkBattle", "HTTP xxx（频控/风控）body=...")`。
3. `PkBattleEngine`：新增 `rateLimitBaseMs`（默认 `RATE_LIMIT_BASE_MS = 60_000`）与 `RATE_LIMIT_MAX_WAIT = 2`；
   - 频控分支：60s → 120s，最多 2 次，**不计入 `maxRetry`**；
   - 非频控的 `PkHttpException`：直接失败（不重试）。

## 待办 12：刷轮数「频控退避」可配（commit `67ff992`）

`PkGrindScreen` 新增 NumberField「频控退避（毫秒，默认 60000）」→ `PkGrindViewModel.start(rateLimitWaitMs = ...)` → `PkBattleEngine(rateLimitBaseMs = ...)`。

# ★★ 2026-10-05 重新取证：揭穿「下限」的两个错误认知

## 一、错误认知 1：把 `self.rank != 999` 当「本局上榜」

**实测证据（2039 负数比大小）**：
- 榜上前 3：5600（时节游戏_蔡徐坤）/ 5630 / 5634；我的行 = **5933 rank40**
- 我近期跑的 4934 / 4984 / 5058 —— **全部没进榜**（榜上最低 5600）
- 但我的 `self.rank` 一直是 40（≠ 999）→ 我就误以为「本局上榜了」

**真相**：`self` 是「**我的历史最佳**」。一旦我在该榜有过成绩，
`self.rank` 永远不是 999，**无论本局是否达标**。

⇒ 判断「本局是否被服务端采纳」的**唯一可靠判据**：
```
self.costTime === 本局 costTime   → 本局成了我的新纪录（被采纳，rank 有效）
self.costTime !== 本局 costTime   → 本局没成为新纪录（无法判断是否达标）
```

## 二、错误认知 2：「完美贴限」的目标错位

因为榜单**只记最佳**，所以：
- 本局优于历史最佳 → 能判断（self 会更新）
- 本局不优于历史最佳 → **永远无法判断本局是否达标**

⇒ 「每局都必须 rank=1」这个目标在**已上榜之后就无法判定**。
正确目标（完美贴限）：**刷新我自己的最佳，使其尽量贴近该榜下限**。

## 三、下限规律（这次坐实了）

每个榜的下限 **= 该榜榜一**，且与**知识点难度**相关（各榜不同）：

| pointId | 知识点 | 下限（=榜一） |
|---|---|---|
| 2035 | 万以内数比大小 | **4900** |
| 2036 | 毫米、分米和千米比大小 | **7000** |
| 2037 | 大数的比较 | **5600** |
| 2038 | 分数比大小 | **5600** |
| 2039 | 负数比大小 | **5600** |

旁证：2035 榜前 15 名有 3 人并列 4900、且 4901/4904/4905… —— 自然分布，
说明 4900 是**真实可达的下限**（不是 clamp 残留）。

## 四、待修

1. `school-season.js` 的贴限核验：把判据改成 `self.costTime === myCost`；
   本局未成为我的新纪录时，**标记为「不可判定」而不是「未上榜」**。

# 结论：一个 Runtime，两个 Core
```
AIForegroundService
  └── Runtime Holder
        ├── MAIN Core     （跟随全局 currentChatId）
        └── FLOATING Core （只维护本地 currentChatId）
```

# 为什么不能共用一个 Core（原文三个理由）
1. 聊天执行链路强依赖 `ViewModel` 生命周期
2. 主界面和悬浮窗靠手工同步消息「看起来一致」，结构更绕
3. 用户想让两边同时操作不同会话时，结构不干净不稳定

# Phase 1-5
1. 建 Runtime 宿主，持两个 Core，`getCore(slot)`（`enum ChatRuntimeSlot { MAIN, FLOATING }`）
2. 补齐 chat 选择隔离（`FOLLOW_GLOBAL` vs `LOCAL_ONLY`，或 `followGlobalCurrentChat: Boolean`）
3. `ChatViewModel` 只接 MAIN Core，删除内部 delegate 装配
4. `FloatingChatService` 只接 FLOATING Core，删除自己的 `chatCore = ChatServiceCore(...)`
5. **删光双向同步**：`setReloadCallback` / `setChatSyncCallback` / `updateChatMessages` / turn complete 后通知主界面 reload

# 两个必须注意的点
- `MessageProcessingDelegate` **不能再用 companion 共享状态**：`sharedIsLoading` / `sharedActiveStreamingChatIds` 必须改为实例内，否则主聊天 loading 污染悬浮窗
- `ChatHistoryDelegate` 的 FLOATING **不能继续订阅全局 `currentChatId`**，否则「两个 Core」只是表面两个实例，chat 选择还是串线

```js
const perQ = max(0, round(target / N - 184));       // 开环公式（已验证）
delayMinMs = delayMaxMs = perQ;
```

`jobs.js`：删掉 `delayAdjMs` 闭环修正（它制造了发散与过冲）。

本轮踩到的三个 Kotlin/API 坑（都是编译期直接报错，记下可省一轮）：

1. **不要自写 `fun String.toMediaType()`**：okhttp 已有 `okhttp3.MediaType.Companion.toMediaType`，自写同名扩展会在 companion 内部解析到自己 → 递归类型推导错误（`Type checking has run into a recursive problem`）。正确写法：`import okhttp3.MediaType.Companion.toMediaType` + `private val X: MediaType = "...".toMediaType()`（必须显式标类型）。

# /verifier/android/sms 服务端行为探测

## 探测方法
`/root/xyks_sms/probe_sms.py`：用不同非法输入调 `POST /verifier/android/sms`，观察响应。

## 探测结果（关键）
| 输入 | HTTP | body |
|---|---|---|
| `12345`（太短） | 200 | 空 |
| `abcdefghijk`（非数字） | 200 | 空 |
| `19999999999`（疑似不存在号段） | 200 | 空 |
| `""`（空字符串） | 200 | 空 |

**结论：服务端不校验手机号格式。** 非法输入与合法输入返回完全一致（200 + 空体）。

## 由此推出
1. **200 不代表短信已发出**：接口只负责"接收 + 解密 + 投递队列"，投递成功即返回 200。真正的格式校验/号段校验/频控在下游短信网关异步做，客户端收不到。
2. **无同步业务错误码**：客户端拿到的反馈只有 HTTP 成功/失败两态。`Llp/d$a` 的 `onFailure` 处理的是网络层错误（连接失败、超时、5xx），不是"手机号格式错"。
3. **频控在连接层**：连续快速请求后出现 `ConnectionError: [Errno 111] Connection refused`，说明有同 IP 频控，但触发点是连接拒绝而非业务响应。

## 修正的旧认知
- 之前以为"200 = 短信发出成功"，实际是"200 = 请求被接收"。
- 之前以为错误码会在 HTTP 层返回，实际不在。

## 2026-10-20 修。现象：登录后不是跳转，而是页面“往下滑一点”。

2026-10-20 修。现象：登录后不是跳转，而是页面“往下滑一点”。

三重根因（叠加）：
1. **主因**：`showApp()` 只做了 `classList.toggle('hidden')`，**没有重置 scrollTop**。登录卡片是 `min-height:100vh + align-items:center` 的满屏居中块，本身不需要页面滚动；主应用是长滚动页。用 display 切换时浏览器不会把 scrollTop 归零 → 长页面“从中间展开”，视觉上就是往下滑。
2. 登录态没有锁页面滚动，所以切换瞬间两个视图高度差全部释放成可滚动区域。
3. 浏览器默认 `history.scrollRestoration = 'auto'`，刷新时会自行恢复上次滚动位置。

修法：
- CSS：`body.auth-mode { height:100dvh; overflow:hidden }`（登录态锁滚动）+ `#appWrap` 淡入动画（不加位移，因为位移会被误读为滑动）。
- JS：新增 `resetScroll()`（`scrollTo({behavior:'instant'})` + 直接改 scrollTop 兜底）与 `setView(mode)`；`setView` 同时切 active、改 body.auth-mode、用 history.pushState 同步 `#/login` ✝ `#/app`。
- 启动时 `history.scrollRestoration = 'manual'`，并加 popstate 处理（已登录时不允许退到登录页）。

关键认知：**用 display 切两个 div 不是“跳转”**，浏览器不会管滚动位置，也不会管 URL。要真正像跳转，必须显式做“锁滚动 + 归零 + 同步 URL”三件。

## 场景：Cloudflare 隧道的 ingress service 写在面板里改不了，它写 https://localhost:7878，而本地端口可能只想给 HTTP，握手必然失败。

场景：Cloudflare 隧道的 ingress service 写在面板里改不了，它写 https://localhost:7878，而本地端口可能只想给 HTTP，握手必然失败。
做法（已在 sxd-host 落地）：用 nginx 的 stream 层 ssl_preread 窥探首字节，TLS record type 0x16 走 TLS 上游，否则走明文上游。
stream { map $ssl_preread_protocol $up { "" 127.0.0.1:7801; default 127.0.0.1:7802; } server { listen 7878; listen 7443; proxy_pass $up; ssl_preread on; proxy_timeout 3600s; } }
7801 是明文反代站点、7802 是 TLS 反代站点，两者都 proxy_pass http://127.0.0.1:8088；proxy_timeout 设长因为 RDP 画面是长连接。
两个必踩的前提：Ubuntu 主包 nginx 不带 stream，需单独装 libnginx-mod-stream；自写 nginx.conf 时最前面必须加 include /etc/nginx/modules-enabled/*.conf; 否则报 unknown directive "stream"。
