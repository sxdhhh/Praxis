```kotlin
val MiuixDefault: NavTransition = navGraphicsTransition(opaqueDepth = 1f) { scope ->
    val width = scope.layoutSize.width.toFloat(); val d = scope.relativeDepth
    val rtl = scope.layoutDirection == LayoutDirection.Rtl
    if (d <= 0f) translationX = ((if (rtl) -1f else 1f) * (-d).coerceIn(0f,1f) * width).fastRoundToInt().toFloat()
    else { translationX = (if (rtl) 1f else -1f) * coverProgress(d) * width * 0.25f; alpha = 1f - 0.1f * coverProgress(d) }
}
```

## ⚠️ 核心硬约束（必须先解决，否则四个 Tab 抢返回权）
`NavDisplay` 内部**自己接管预测性返回**（NavDisplay.kt:470）：`PredictiveBackHandlerWithSessions(enabled = backStack.size > 1, …)`。它是用 `PredictiveBackHandlerWithSessions` 注册的，由栈深决定是否注册。
本项目当前（MainActivity.AppShell）是**四个 Tab 各 rememberNavController() 塞进 HorizontalPager**，每 page 一个 NavHost —— 若照拄成四个常驻 NavDisplay，**四个都会尝试注册预测性返回**，串台。

参考项目的解法（cn.nizou.sxd/ui/MainPagerScreen.kt）：**单一 NavDisplay，根 entry 内部才是 pager**：
```kotlin
val backStack = rememberNavBackStack<MainRoute>(MainRoute.Main)
val navigator = remember(backStack) { Navigator(backStack) }
val pagerState = rememberPagerState(pageCount = { MAIN_TABS.size })
CompositionLocalProvider(LocalNavigator provides navigator) {
    NavDisplay(
        backStack = backStack,
        onBack = { if (navigator.backStackSize() <= 1) backAtRoot() else navigator.pop() },
        transition = weKitNavTransition(ThemeSettings.pageTransitionAnimation),
        effects = rememberM3NavEffects(),
    ) {
        entry<MainRoute.Main> { MainPager(res, pagerState, onNavigate = { navigator.push(it) }, onBackAtRoot = ::backAtRoot) }
        entry<MainRoute.General>(swipeDismiss = NavSwipeDirection.LeftToRight) { … }
    }
}
// 返回：栈深>1 → pop；栈深==1 且非首页 tab → 先回首页 tab；首页 tab 再触发 onFinish()
BackHandler(enabled = navigator.backStackSize() == 1 && pagerState.currentPage != 0) { … }
```
**结论**：本项目应改成「单一 NavDisplay + 根 entry 内放 pager」，而不是四个 NavDisplay。备选（非当前 Tab 不参与组合）会丢各 Tab 返回栈状态保持，与用户 2026-09-25 拍板的「结构 A：每 Tab 独立返回栈」冲突 —— 所以单一 NavDisplay 是唯一同时满足两边的写法。

# ★★ 最关键发现：miuix MonetSystem 不一定读壁纸
源码 `miuix-ui/.../theme/ThemeController.kt` 的 `currentColors()`：
```kotlin
ColorSchemeMode.MonetSystem -> {
    val dark = isDark ?: isSystemInDarkTheme()
    keyColor?.let { remember(...) { colorsFromSeed(it, colorSpec, paletteStyle, dark) } }
        ?: platformDynamicColors(dark)     // ← 只有 keyColor == null 才读系统！
}
```
→ **传了 keyColor 就永远不走 platformDynamicColors**，只是把 keyColor 摊成调色板。
这解释了 suchat 当年“永远固定绿”的根因。

# Praxis 正确用法
| 意图 | 做法 |
|---|---|
| 跟壁纸 | `MonetSystem` + **keyColor = null** |
| 用自选色 | `MonetSystem` + `keyColor = seedColor` |

```kotlin
fun rememberKeyColor(useDynamic, seedColor): Color? =
    if (useDynamic && SDK_INT >= S) null else seedColor
```

# miuix 真实取色链（platformDynamicColors，Android 实现）
| API | 行为 |
|---|---|

本次拿 contents 响应重试到第 7 次才成功。

### 坑 3：大传输（git pack / tarball）几乎必断
- `git clone` → `transfer closed with outstanding read data remaining`
- `git clone --depth 1` → `Empty reply from server`
- tarball → 50s 超时
**所以不能用 clone 来验证**，改用 `contents/<path>` 这种小响应接口逐个抽查。

### 坑 4：POST 建仓库「响应超时但服务端已成功」
第一次 POST /api/repos 实际创建成功，但响应回程超时 → 脚本误判失败；第二次再 POST 得到 422 `Repository already exists`。

4. **分级保鲜**：app 每次查询都查；miuix/sxd 按 `COLD_TTL_SEC=300s` 兜底。`-s` 完全跳过。
5. **「0 命中 → 全量重建重试」+ 世代护栏**：快速保鲜看不见新增文件，所以 0 命中时重建一次再试；用 `meta.last_index` 做世代标记，同一世代只重试一次。
6. `meta` 两键勿混：`last_check`（每次保鲜写，供 TTL）/ `last_index`（仅 changed>0 写，是索引世代）。
7. 单次调用 ~150~250ms 构成：sh 8 + `python3 -S` 40 + 导入 34 + 开库 10 + 查询 5~20 + 保鲜 40~60。`-S` 省 ~45ms。

9. **`repo` 过滤不能写成 `set(ids) if ids else None`**：空列表是 falsy → 过滤被静默取消，会返回**全库**结果（曾把已删的 mem 当成「不过滤」）。正确写法：给了 repo 就按它过滤，且无命中时**短路返回 0** 并提示可用 repo。
10. **删目录不会自动清索引孤儿行**：`build()` 只覆盖「本次传入的 repo」，所以要单独跑 `python3 /root/cx/purge_repo.py <repo>` 清（内部会重建 FTS）。
11. 查询时不要一次响应里并发多个 `package_proxy` 块（会串输出），宁可串行。

## ★ Android 上「杀子进程」的三条硬约束（全部真机实测，不是推测）

# ★ Android 上「杀子进程」的三条硬约束（全部真机实测，不是推测）

背景：老挂的内置终端要给 `sh -i` 做「Ctrl+C」，结果连撞三层墙。
这三条对**任何**「Android 上跑子进程并要控制它」的场景都通用
（内置 node、终端、未来的其他 native 子进程）。

## 坑 1：`java.lang.Process.pid()` 在 Android 上**不存在**

它是 **Java 9+** API，Android 只有 Java 8 那套。
→ 无法从 `Process` 对象拿到子进程 pid。

**解法**（让 shell 自己报 pid）：
```sh
/system/bin/sh -c 'echo $$ > <pidfile>; exec /system/bin/sh -i'
```
关键是 **`exec`**：它**替换进程映像而不是 fork**，所以 pid 不变，
pidfile 里记的就是最终那个交互 sh 的 pid。

⚠️ 本项目在 `NodeRuntime` 上也栽过同一个坑（当时用 `Log.i(..., p.isAlive)` 绕过）。

## 坑 2：`/proc/<pid>/task/<pid>/children` 在 Android 上**读不到**

这是 Linux 上「列出子进程」的标准做法，真机实测：
```
children_file_UNREADABLE
```
（内核/SELinux 就把它做成不可读，`ps` 与 `/proc` 两条路都堵。）

**解法**：改用 `ps -o PID,PPID`，然后按 PPID 过滤：
```sh
ps -o PID,PPID 2>/dev/null | awk -v p=<hostPid> '$2==p {print $1}'
```
实测在 Android 上**同 uid 能列出自己的子进程**
（`ps -o PID,PPID` 会输出全系统进程列表，其中包含 PPID == 当前 sh 的那几条）。

## 坑 3：管道 shell **没有 job control**

`sh -i` 配 `ProcessBuilder` 走的是**管道**而不是 pty → sh 不知道「谁是前台任务」，
也没有 `^C` 按键可转发。只能由 App 侧枚举子进程逐个 `kill`。

## ★ 关键设计：**永远不要给 sh 自己发 SIGINT**

管道模式下 sh 收到 SIGINT 可能**直接退出**（而不是「中断当前行、回到提示符」），
那样用户按一次 Ctrl+C 就把整个终端弄死了。**只发给子进程。**

## ★★ 关终端时的孤儿陷阱（最隐蔽）

父进程（sh）一死，它的子进程会被 **reparent 到 init（PPID=1）**，
于是**再也按 PPID 找不到它们** → 它们继续跑、继续占着端口
（下次启动 node 就报「端口被占用」）。

所以停止顺序必须是：
1. **先** SIGINT 子进程（正常中断，让它们自己收拾）；
2. `sleep 300ms`（SIGINT 可以被忽略/捕获）；
3. 还活着的**补 SIGKILL** —— 必须**在 sh 死之前**做；
4. **最后**才 `destroy()` sh 自己。

## 附带

- 可用性：`/system/bin/kill`（toybox 符号链接）、`pgrep` / `pkill` / `setsid` / `ps` 都在（实测）。
- **近似性要如实写进 KDoc**：这是「近似 Ctrl+C」，会中断 sh 的**所有**子进程，
  包括用户自己 `&` 放后台的。真 job control 需要 PTY。

# Praxis 典型缺陷形态（都在本项目真实发生过，重复率很高）

## 1. 「三层各写对一半」
温度滑块曾因三处叠加而从未生效：`ChatRequest.temperature` 默认写死 0.7；`ChatViewModel` 构造 ChatRequest 时不传 temperature；`SettingsBackedProvider` 只 `request.copy(model=...)`。单看任一层都对。
→ 只能跟到请求体才能发现。

## 2. 「组件齐全却未接线」
已发生四次：MEMORY / WORKFLOW 域的 MemoryRoute / WorkflowRoute 早已写好、有真实数据，却只在 SETTINGS 域被调用；底栏玻璃曾因“依赖在 gradle 里 + LocalKyantBackdrop 定义了”被标「已达成」，实际零调用。
→ 判「已实现」必须有生产调用链，不是依赖存在。可用 `grep -rn 'funName(' --include=*.kt` 反查调用点。

## 3. 「事件/判据语义错」
- `LaunchedEffect(Unit)` 只比 key，Unit 永远等于 Unit，不知道闭包捕获的对象已换实例（会话切换是换 ViewModel 实例）→ 新会话永远不加载。key 要写对象本身。
- `last == null` 本意是“还没测量”，却被当作“已经到底”（AutoFollowScroll 第 10 轮根因）。
- 浮点比较不带容差→「已保存」永不显示。

## 4. 「静默删数据」
Room `@Insert(onConflict = REPLACE)` 等价 DELETE+INSERT，配合 `ON DELETE CASCADE` 会静默删光子表。已改为先 find 再 insert + `UPDATE`。任何一处回退都会静默删光历史。

## 5. 「异常被压成一个 false」
`runCatching{}.getOrDefault(false)` 把磁盘满/TLS/DNS/超时/404/截断六种故障压成同一个 false，界面只剩“下载失败”。应改 sealed Outcome + 逐条报告 + 可操作建议（httpReason(code)）。

## 6. 「Compose 编译期硬禁止」
- `try { content() } catch {}` 包 composable **编译不过**（`Try catch is not supported around composable function invocations`）——组合靠位置配对 group key，异常会让 insert/end group 不配对。错误边界组件不可行。
- `LazyColumn` 单个 item 内放多个 composable 会全部堆在 (0,0)，必须包 Column。
- `Modifier.fillMaxSize()` 写在调用方约束之后会覆盖约束；`Row(Modifier.fillMaxSize())` 是横向容器撑满高度。
- `items(list)` 不给 key 会在滚动/增删时行内容错位；`items(count){index->}` 同。

## 7. 「注释/提交信息里的出处是错的」
曾写「照抄 apixiaoyuan 的原生写法」，实际那段代码出自 `cn.nizou.sxd/CustomScoreScreen.kt:317`。
→ 凡写「照抄 A 的某实现」，必须先在该仓 grep 到路径+行号写进注释；grep 不到就不写。

## 1. 自研动画 vs 原生动画的判断标准
**凡是能用 Compose 原生滚动/动画 API 表达的，不要自研。**
自研 `withFrameNanos` + `scrollBy` 会与 `LazyColumn` 自己的 fling/吸附/边界逻辑直接冲突，表现为「追一下顿一下」。
原生 `animateScrollToItem` 自带插入、取消、衔接、中断处理 —— 这些东西自己重写必然漏。

## 2. `LaunchedEffect(key)` 的 key 选择会毁掉动画
`LaunchedEffect(itemCount)` 在流式递增时频繁重启，协程内累积的状态（速度、lastFrame）全部丢失。
apixiaoyuan 的写法只用 `itemCount` 作为「要不要开始一次新动画」的触发条件，动画本身由 Compose 维护，所以不丢。
区分：“重新开始一段动画” vs “每帧手动推”——前者可用 key，后者绝不能用频繁变的 key。

## 3. 浮层底栏 + 固定输入栏的双重占位陷阱
当一个页面同时有「浮层底栏」与「吸底输入栏」时，**两者都要抬高**：
- 输入栏 `bottomPadding = scrollLimit`（不然输入栏被底栏遮）；
- 列表 `contentPadding.bottom += scrollLimit`（不然最后一条被输入栏/底栏遮）。
只抬一个的话，用户能看到输入栏但却看不全最后一条消息 —— 本次 ChatScreen 与 TerminalScreen 同时中招。

## 4. apixiaoyuan 可复用件位置（已取证）
- 自动跟随：`cn.nizou.sxd/app/.../ui/settings/CustomScoreScreen.kt:307-319`（20 行，原生 animateScrollToItem）

## 结论：正确实现 = hook 宿主自己的校验器，不要 hook 框架热路径

# 结论：正确实现 = hook 宿主自己的校验器，不要 hook 框架热路径
权威来源：`cn.nizou.sxd`（老挂戏老叟）`app/src/main/java/cn/nizou/sxd/hook/NicknameHook.kt`
（2026-08-29 真机事故后定案；用户 2026-09-26 再次拍板「AOC 自定义名字不行，老挂戏老叟的最好」）

## 正确实现（两段，由单一开关 `Common.ignoreNicknameRestriction` 控制）
1. 字符/格式限制：拦截 `Pattern` 构造器，把昵称 Pattern 换成 `[\S]*`（任意非空白字符）。
2. 长度限制：hook 宿主自己的 GBK 字节长度计算 `cs.p7.a(String):Int`，开关打开时直接返回 0。

关键点：`cs.p7.a` 是**宿主自己的校验器**（全宿主仅被 `c(nick)` 调用、非热路径），因此没有递归风险。注释还确认 `c(nick)` 的规则是 GBK 字节长度 ≤ 16，格式另由 `jv.j.b` 校验。

## 禁止方案：hook 框架方法 `java.lang.String.getBytes(Charset)`
第三方项目 AOC（`TinyHai/AutoOralCalculation`）的 NicknameHook 就是 hook `String.getBytes(Charset)`，GBK 时把返回字节数组截半。

危害（老挂戏老叟注释里有真机证据）：对 `String.getBytes(Charset)` 的 hook 在 **LSPosed(standard)** 下会引发宿主主线程**无限递归**——真机 ANR `Process failed to complete startup`，主线程 `getBytes → printStackTrace` 死循环，堆 512MB OOM。原因：LSPosed 的 hook 桥在序列化/toString/打异常栈时会再次调 `getBytes`，每次递归又进本 hooker，`proceed` / `getInvoker(ORIGIN)` 都打不断。

结论：**hook 框架热路径方法（String.getBytes）是错误方案，会 ANR/OOM，勿使用。**

# 坑的本质
