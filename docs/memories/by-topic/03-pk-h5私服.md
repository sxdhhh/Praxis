## 二、Praxis FTP 实现（本轮，架构不同）

**关键决策：不照抄 Apache FtpServer，改走「容器内 vsftpd + 脚本生成」**，与既有 `SshdScript`/`FrpScript` 同构。理由（已写入 KDoc）：
1. JVM 进程直读 rootfs 会绕过 proot 的 uid 映射，文件属主/权限解释不一致；
2. 生命周期必须统一走 `LinuxToolPort.startSession`（随容器启停、日志回流），否则「容器停了 FTP 还在跑」。

新建 `core/linux/FtpServer.kt`（347 行）：
- `FtpConfig(port=2127, passivePorts="2128-2136", user="ubuntu", homeDir="/home/ubuntu")`
- 校验：`isPortUsable`（≥1024）、`portProblem`（含 **2222 与 SSH 冲突**检测）、`isPassiveRangeValid`、`passiveRangeProblem`、`isUserUsable`
- `FtpServerScript.installScript` / `setPasswordScript` / `runArgs` / `passiveRange` / `shellQuote`

**proot 三大坑（已写进配置与 KDoc）**：
1. `allow_writeable_chroot=YES` —— 缺则 `500 OOPS: refusing to run with writable root inside chroot` 直接拒启；
2. 极简 PAM `/etc/pam.d/vsftpd.praxis` 只有 `pam_unix`（系统版含 `pam_loginuid`/`pam_systemd`，proot 下失败 → 任何密码都登不进）；
3. `pasv_enable=YES` + 固定 `pasv_min_port/max_port`（缺则客户端登录成功但 LIST 卡住、看不到文件）。

其他配置：`listen=YES`+`listen_ipv6=NO`（proot 无 IPv6）、`anonymous_enable=NO`、`local_enable=YES`、`write_enable=YES`、`chroot_local_user=YES`、`utf8_filesystem=YES`（中文名）、`ssl_enable=NO`、`xferlog_file=/var/log/vsftpd.praxis.log`、`max_per_ip=3`、`idle_session_timeout=120`、`use_localtime=YES`。

`runArgs`：`/usr/sbin/vsftpd -obackground=NO -olisten=YES -oport=P CONFIG`（`background=NO` 保证进程生命周期 == 会话，否则 UI 状态永久错位）。

接线：`LinuxEnvUiState` 加 `ftpEnabled`/`ftpConfig`；`LinuxEnvViewModel` 加 `ftpSession` + `updateFtpConfig`/`toggleFtp`/`setFtpPassword`/`applyFtp`/`stopFtp`，并在 `stop()` 里联动 `stopFtp()`；`LinuxEnvScreen` 在 SSH 与 FRP 之间插 FTP 卡片（段落序：直连→文件传输→穿透）；`LinuxEnvRoute` 插 3 个回调。

## 一、终端间距修复（第 1 轮，真实 bug）

**根因**：`scrollLimit`（浮层底栏 ≈ 64+12+navBar ≈ 90dp）被**让了两次**。

`keyboardBottomInset` = `scrollLimit - imeLift`。键盘收起时 `imeLift = 0`，该值就等于整个 `scrollLimit`。而 `TerminalInputBar` 与 `TerminalVirtualKeyboard` **两处都在让**这个值。

`feature/terminal/.../TerminalScreen.kt` 修改（1 行核心 + 11 行说明）：
```kotlin
paddingBottom = if (keyboardVisible) 0.dp else keyboardBottomInset,
```

语义：底栏占位**只能由 Column 最底下那一段让出一次**。布局序 `[输出区][操作条][输入条][虚拟键盘]`：
- 虚拟键盘收起 → 最后一段是输入条，由它让；
- 虚拟键盘展开 → 最后一段是虚拟键盘，由它让，输入条让 0。

`keyboardVisible` 初值 `false`（`rememberSaveable`），已核实。

## 二、文件工具补全（第 3 轮，真实缺口）

`core/tool/.../builtin/FileTools.kt` 236 → **490 行**，4 → **8 个工具**。新增：

| 工具 | 为何值得单独存在 |
|---|---|
| `file_exists` | 用 read_file 探会浪费 token 或把「不存在」误判为错误；不存在**不算错误**（`isError=false`） |
| `file_info` | 不知道大小就直接 read_file 会撞截断；目录报 entries 而非 length（后者误导） |
| `move_file` | 改名不必 write+delete（大文件翻倍写、丢元数据） |
| `copy_file` | 备份一个文件都做不到 |

**关键安全点**：`move_file` / `copy_file` 必须校验**两端**路径（只校源端就能把文件移出沙箱，`to=../etc/passwd`）。

设计取舍：`copy_file` **不支持目录**（递归要处理符号链接环/权限/部分失败回滚 = `cp -r` 的复杂度），提示用已有的终端会话工具跑 `cp -r`。`move_file` 失败时提示跨文件系统 + 改用 copy+delete。

## 三、消息变体（第 4 轮，数据层）

**依据**：`feature/chat/ChatState.kt:494` 自己写着「删除当前变体 | （无）| 需要消息变体模型（`variantCount`）」，即已知未实现。

**问题**：`retry()` 会**再插一条 assistant 消息**。重试 3 次 = 4 条并排回答，前 3 条是垃圾，**而且都会进上下文被送给模型**。

`app/.../db/MessageEntity.kt` 加两列：
- `variantGroupId: String? = null`（null = 普通消息）；
- `variantIndex: Int? = null`（组内 0 起序号）。

两列都用 NULL 而非 `NOT NULL DEFAULT ''`：否则「不属于任何组」与「组 id 是空串」混成一种表示，查询得额外写 `!= ''`，忘写就把所有普通消息当一组。

新增索引 `Index(value = ["sessionId", "variantGroupId"])`（列序不能反）。

`PraxisDatabase`：**version 6 → 7**，新增 `MIGRATION_6_7`（两列 ADD COLUMN + 建索引）。

- `AppModule` 已注册 `MIGRATION_6_7`。

## ★★ 2026-10-05：低版本玻璃从 CPU 改成 **GPU（OpenGL ES 2.0）** + 五项反馈修复

# ★★ 2026-10-05：低版本玻璃从 CPU 改成 **GPU（OpenGL ES 2.0）** + 五项反馈修复

用户一句「gpu 加速不就行了」点醒了我 —— 上一版用 CPU 逐像素算折射，用户实测「延迟有点大」。**AGSL 是 GLSL ES 3.0 的超集，而 GLSL ES 2.0 从 Android 2.2（API 8）就有** —— 直接翻过去，在 GPU 上跑。

提交：`579d69d`（主管线）+ `45b19df`（修真机 Bitmap 格式）。CI 全绿。

## 一、为什么 GPU 才是正解

1. **快几个数量级**：GPU 几千核心并行；CPU 一行一行来。折射从几百 ms 降到 1–3 ms。
2. **更接近 1:1**：AGSL 与 GLSL 同为**GPU 着色器语言** —— 浮点行为、纹理双线性插值、clamp-to-edge 都由 GL 规范保证，与 AGSL **天然一致**。CPU 版还得自己模拟双线性采样，必然有差异。

## 二、AGSL → GLSL ES 2.0 翻译表（`low/gl/GlassShaders.kt` 有完整表）

| AGSL | GLSL ES 2.0 |
|---|---|
| `half4 main(float2 coord)` | `void main()` + `gl_FragColor` |
| `uniform shader content` + `content.eval(c)` | `uniform sampler2D uContent` + `evalContent()` |
| `coord`（**左上**原点像素坐标） | `vec2(gl_FragCoord.x, uSize.y - gl_FragCoord.y)` ← **必须翻 Y** |
| `half4` 精度 | `precision highp float`（`#ifdef GL_FRAGMENT_PRECISION_HIGH` 兜底） |

**唯一「非逐字」的改动就是坐标系翻转**（GL `gl_FragCoord` 是左下原点）。翻完其余可逐字照抄。

## 三、渲染器架构（`low/gl/GlGlassRenderer.kt`）

源 Bitmap → 纹理 A → ①模糊H(ping-pong 到B) → ②模糊V(B→A) → ③折射(A→B) → FBO → glReadPixels → 输出（垂直翻转）

- **EGL 上下文必须同线程** → 内部专用单线程执行器（`low-glass-gl`），调用方同步等。
- 上下文/程序/纹理/FBO **常驻复用**（重建 EGL 要几十 ms）。
- 模糊用**可分离高斯**（两趟，σ=radius/2、3σ 截断）。
- 纹理必须 `GL_CLAMP_TO_EDGE`（与 AGSL `eval` 边界一致，**不能 REPEAT**）。

## 一、`{client}` → `api` 的机制（H5 源码逐字）

`assets/request-legacy.CdI7tZrH.js`（axios 请求拦截器，整个文件只有 1278 字节）：

- `a()` = 某个设备判定、`f(ver)` = `greaterThanOrEqualTo(ver)`；

## 我之前的错误结论（已推翻）
> 「H5 两个 axios response 拦截器都原样返回、全资产无 dataDecrypt 调用，
>  ArrayBuffer → 对象 这层是真机原生 WebView 做的」

## 实际代码（exercise-legacy.C5DFMay0.js，位于 getPkExerciseQuestionV2 定义之前）
```js
// 响应拦截器：对 arraybuffer 响应自动解密
var u = (e, n, a) => {
  var i = a.value;
  var o = wrap(i, function (...args) {
    return i.apply(e, args).then(function (resp) {
      var b64 = btoa(String.fromCharCode.apply(null, new Uint8Array(resp)));
      return l(b64);          // → 调桥 dataDecrypt
    }).catch(t => { throw t; });
  });
  a.value = o; return a;
};

// l：调原生桥解密，拿到 base64 明文 → JSON.parse
var l = (b64) => new Promise(resolve => {
  i('dataDecrypt', { base64: b64, trigger: (err, r) => {
       resolve(JSON.parse(Base64.decode(r.result)));
     }}, 'LeoSecure');
});
```

**关键结论**：H5 **自己会解密**，但解密动作**必须由原生桥 LeoSecure.dataDecrypt 完成**
（因为 keystream 在 Android so 里，浏览器没有）。

而我们的桥没有 dataDecrypt：
- bridge-miss → METHOD_NOT_SUPPORT → 回调首项非空 → H5 当失败；
- 更常见的是 Promise 挂着不动 → **界面永远「匹配中」**。

## 实现（ea9a075）
1. **server.js**：新增免鉴权端点 POST /api/pk/h5/decrypt
   - 入：{ base64: <密文> }
   - 出：{ ok:true, result: <base64 明文 JSON>, size }
   - 内部：pkH5.decryptBuffer（keystream XOR → 判 gzip → gunzip）
   - needAuth() 白名单加上它（否则 401）。
2. **pk-h5-proxy**：导出 decryptBuffer: decodeEncrypted。
3. **浏览器 hook**：
   - nodeDecrypt(b64)：用 XHR POST 上述端点；
   - HANDLERS.dataDecrypt：异步返回 { __pkOut: [null, { result: <base64> }] }
     （对齐真机桥的 res.result 契约）；
   - dispatch 支持 Promise 处理器（提前 return true 避免重复回调）；
   - 同步返回值统一包 [null, v]，METHOD_NOT_SUPPORT 保留裸数组。

patchArrayBufferResponse（XHR response getter 重写）：把 arraybuffer 转成对象，
而 H5 随后又把它序列化去 dataDecrypt → 必然失败。是**错上加错**，已删。

# ★★ 真凶：桥的 trigger 有「两种语义」—— setter 类不能回调（2026-09-30，a10883e）

## 现象
点「PK榜」→ 荣誉榜页（motivation-honor-roll）打开 → 约 4ms 后**自己退回 PK 主页面**。

## 真因（日志时序铁证，间隔仅 2ms）
```
341994 bridge-call setLeftButton   cb=setLeftButton_1790694341994_24
341996 bridge-call sendEventToNative eventName=exercise_motivation_back_pk
341996 bridge-call closeWebView     → [null,"OK"]
```

页面代码（motivation-honor-roll-legacy.COVgsFc6.js）：
```js
f = () => {
  m.postMessage({eventName:'exercise_motivation_back_pk', ...});   // 埋点
  s();                                                            // s() = closeWebView()
};
return r({ block: true, trigger: () => { f() } });   // setLeftButton 的返回键处理器
```

**H5 的 trigger 有两种语义**：

| 类型 | 例子 | trigger 的含义 | 我们该怎么做 |
|---|---|---|---|
| **查询类** | getUserInfo / getWebViewInfo / requestConfig | **回执回调**，页面注册 window[trigger] 等结果 | 必须 unshift 结果把 Promise resolve 掉 |
| **setter 类** | **setLeftButton** / setOnVisibilityChange / refreshStateView / setForceBounceEnable / observeTabChange / ShowPracticeDialogIfNeeded | **事件处理器**，只登记，等用户真按键才回调 | **绝不能主动回调** |

我们一律 window[cbName](base64([...])) → 对 setter 类等于**替用户按下了那个键**
→ 返回键被按下 → closeWebView → 页面自己关闭。

> 之前 PK 首页没暴露这个问题，是因为它没有 setLeftButton 这类调用；
> 荣誉榜页有（导航栏返回键），一进去就被我们按了。

## 修法（a10883e）
1. parsePayload 拆开两个回调：receiptName（= obj.callback）与 cbName（= h.trigger）。
2. reply(p, out)：① 先回 receiptName（若有）；② if (p.skipTrigger || !p.cbName) return; 否则回 trigger。
3. 新增 NO_TRIGGER_METHODS 白名单；dispatch 里对这些方法设 p.skipTrigger = true。

## 一、★ 我之前的假设是错的（要记牢）

旧代码在 `PkH5Screen` 构造 WebView 时写了：

```kotlin
// 为规避 Compose 重入合成崩溃
isFocusable = false
isFocusableInTouchMode = false
```

并配了一句注释断言：

> 「HTML 输入焦点走 chromium 内部子 View，不依赖 WebView 自身可聚焦」

**这句是错的。** Chromium **不用子 View 承载输入框** —— 它直接在 **WebView 自身**上
建立 `InputConnection` 并 `requestFocus` 请求 IME。所以：

> `isFocusable = false` 的代价 = **整个 H5 页面永远弹不出输入法**（所有 `<input>` 都敲不了字）。

用户反馈「调不出输入法」正是这条。

## 二、真正要防的是什么

崩溃栈（`data_app_crash@1790394023891`）：

```
Choreographer.doFrame → Compose applyChanges
  → ViewGroup.removeViewInLayout
  → View.rootViewRequestFocus
  → AndroidComposeView.requestFocus
  → "pending composition has not been applied"
```

机理：被移除的 View 正是 `mFocused` 时，ViewGroup 会向上重新找焦点持有者，
而此刻 Compose 正在 apply 阶段 → 重入合成 → 崩。

**触发条件只是「移除时还持着焦点」**，并不是「可聚焦」本身。
所以正确解法是：**允许聚焦，但保证移出视图树之前清掉焦点**。

## 三、落地（当前做法）

```kotlin
isFocusable = true
isFocusableInTouchMode = true
descendantFocusability = android.view.ViewGroup.FOCUS_BEFORE_DESCENDANTS
```

三处 clearFocus（缺一不可）：

| # | 位置 | 时机 | 说明 |
|---|---|---|---|
| 1 | `goBackOrFinish()` 的 **else 分支** | onFinish 之前 | ★ 本次补上，之前**漏了**（KDoc 说有、代码里没有 → 文档与代码不符，本身就是 bug）|
| 2 | `DisposableEffect.onDispose` | 与合成同帧，**早于** onRelease | 「View 被摘掉之前的最后一次清焦点机会」|
| 3 | `releaseWebView()`（`AndroidView.onRelease`） | View 已移出后 | 第一步就 `clearFocus()` |

⭐ **`goBackOrFinish()` 的 `goBack()` 分支刻意不清焦点**：
用户可能正在某个 `<input>` 里打字，退一级不等于要收起输入法（浏览器也是这行为）。
只在「真的要离开容器」（`canGoBack()==false` → onFinish）时才清。

`leo://close|back|finish` scheme 那条路拿不到 webView 实例（`handleScheme` 只收 url），
只能靠 onDispose / onRelease 兜底；BackHandler 那条路已由 `goBackOrFinish` 提前覆盖
（最常见场景）。

## ★ 排行榜「打不开」真因：H5 的「本地环境禁用原生桥」门禁（2026-09-30，2b5ae77）

# ★ 排行榜「打不开」真因：H5 的「本地环境禁用原生桥」门禁（2026-09-30，2b5ae77）

## 现象
登录态已恢复（console 回传显示 `>>>>>>>>>最终结果 0 [{userId:1155551346,...}]`），
但点「PK榜」→ 页面渲染出来**但内容空白**，且该页**一个数据请求都不发**（没有 rank/list）。

## 真因（console 回传直接给出）
```
[Bridge] Provider "NativeBridgeProvider" 已注册，当前优先级: NativeBridgeProvider
[Bridge] 没有 Provider 可以处理 "getWebViewInfo"    × 14
```

逐行读 `leo-web-study-group/assets/index-legacy.UF8C8ODn.js`：
```js
tA = function () {
  var t = window.location.hostname;
  return "local.yuanfudao.biz" === t || "127.0.0.1" === t || "localhost" === t;   // 本地调试判定
};
BA.prototype.has = function (t, A) { return !tA(); };   // NativeBridgeProvider.has
```

**H5 把「本地调试环境」判定为「禁用原生桥」**（has=false）。
而我们为了同源代理**必须**跑在 127.0.0.1 → 恒真 → has 恒假
→ 新版 Bridge 框架一个方法都不接 → 榜单初始化失败 → 不发请求。

> 这是「浏览器里模拟 App」的结构性死结：**同源代理必须用 127.0.0.1，
> 而 H5 恰好用 hostname 判断你是不是在真机。**

## 修法（资产级改写）
新增 rewriteAssetJs()：对代理过来的 JS 资产做最小改写（HTML 之外）：
  return"local.yuanfudao.biz"===t||"127.0.0.1"===t||"localhost"===t
  → return false/*__pkNotLocalHost*/
幂等（__pkNotLocalHost 标记），只动这一处，让 H5 以为在真机环境。
验证：curl /pk-h5-cdn/leo-web-study-group/assets/index-legacy.UF8C8ODn.js
→ 返回 return false/*__pkNotLocalHost*/，日志打印「已改写本地环境门禁」。

## 可复用的方法论
1. **console 回传是杀手铜**：H5 自己会把关键状态 console.log 出来（例如
   >>>>>>>>>最终结果 <err> <extData>），把它接回服务端，比猜代码快一个数量级。
2. 「页面渲染出来但**零数据请求**」= 桥/初始化环节被前置门禁拦住了，不是网络层问题。
3. 遇到 [Bridge] 没有 Provider 可以处理 "xxx" 就去查 Provider.has() 的判据，
   不要只看 callNative 实现。
4. **代理不仅仅是转发**：必要时对 CDN 资产做**最小语义改写**（本次改一处 return），
   这是浏览器复现 App 场景的关键手段。

## 相关
- 排行榜的真实接口：GET /leo-star/{client}/exercise/rank/list（new 版，来自
  medal-wangzhe-legacy），旧版才是 /leo-homework/{client}/daily-practice/rank/info。
- host 白名单已改通配 *.yuanfudao.com（leo-homework / leo-activity /

## 2026-10-26 在 sxd-host 上把 ClawDesk 网页远控（Guacamole + gnome-remote-desktop RDP + Cloudflare Tunnel）跑了起来，并定位了两个真 bug 与一个外部卡点…

2026-10-26 在 sxd-host 上把 ClawDesk 网页远控（Guacamole + gnome-remote-desktop RDP + Cloudflare Tunnel）跑了起来，并定位了两个真 bug 与一个外部卡点。

入口状态：quick tunnel https://amazing-cargo-technical-cas.trycloudflare.com/guacamole/ 返回 200；本地 http/https 127.0.0.1:7878 均 200；面板域名 sxd.sxdshh.kdns.fr 返回 000。账号 clawdesk（完整远控）、clawview（只读），口令不入记忆。

真 bug 1：/etc/cloudflared/token 是 0 字节文件（cloudflared service install 写 token 时 sudo 与 heredoc 混用失败）。表现为 systemctl is-active 显示 active，但日志里没有一条 Registered tunnel connection，公网访问 000。重写 token（root 600）并重启后出现 4 条 Registered tunnel connection（lax08/sjc05/sjc11，QUIC）。结论：判断隧道是否真连上只看这条日志，不看 systemctl is-active。

真 bug 2：隧道 ingress 下发的是 https://localhost:7878，而 7878 当时是 socat 裸转发（纯 HTTP），云端 TLS 握手必失败→隧道 502。改用 nginx stream + ssl_preread，让 7878/7443 同端口同时接 HTTP 与 HTTPS，上游 7801(明文)/7802(TLS) 都反代到 127.0.0.1:8088，从此面板填 http 还是 https 都能工作。

RDP 凭据：GNOME 50 的 grdctl rdp set-credentials 不写文件、写 keyring（schema org.gnome.RemoteDesktop.RdpCredentials）；在无 X11 的 SSH 里必须先 export XDG_RUNTIME_DIR=/run/user/1000 与 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus，否则静默失败；~/.local/share/gnome-remote-desktop/ 下只有 rdp-tls.crt/key，没有 credentials 文件，导致 Guacamole 报登录失败。

DNS 卡点（外部，需在面板侧处理）：sxdshh.kdns.fr 的 zone 在 Cloudflare 状态为 pending，CF 要求 NS 改为 elly.ns.cloudflare.com 与 felipe.ns.cloudflare.com；该子域此前由 ns1~ns4.katabump.fr 权威、由父域 kdns.fr 委派。用户改 NS 后 NS 查询出现空结果，处于切换过渡。用户给的 cfat_ 令牌实测是 R2 的 S3 令牌：user/tokens/verify 返回 Invalid API Token，但能调 zones / accounts / cfd_tunnel 三个接口。

环境事实：该机是 Wayland GNOME，x11vnc 抓不到 GNOME 窗口（截图为空白），x11vnc + noVNC 教程在此不成立；只能用 gnome-remote-desktop（Wayland Portal 原生 RDP）+ Guacamole 做 HTML5 转换；guacd 在 apt 里没有包，只能跑 Docker。

> 「然后那个 js 控制台配置要持久化」

## 一、先澄清一个容易搞错的事实

`OldSimianPrefs.h5DebugConsole`（也就是「JS 控制台」那个**开关**）
**本来就已经在 `persist()` / `init()` 列表里**，重启后不会丢。

所以「要持久化」指的**不是那个布尔开关**，而是 **Eruda 自身的配置**：
面板的重启后总是回到默认（固定 `defaultPanel:'console'`、时间戳每次重新设、
面板位置/尺寸等全丢）。根子在于**每次加载都从 `assets/js/eruda.js` 重读 474KB 重注入**，
任何 Eruda 自己存的东西都没有立足之地。

## 二、改法：把 Eruda 脚本缓存进 WebView 的 localStorage

`PkJsInjector` 的 Eruda 段改成「页面侧判定 + 原生按需供给」：

```
页面侧一段 JS 依次判定：
  1. !document.head        → 'NOTREADY'（还没加载完，等下次 onPageFinished）
  2. eruda._isInit         → 'DONE'    （本次加载已初始化，防 SPA 内部导航叠多个面板）
  3. localStorage 有缓存   → 直接 (new Function(src))() 执行，返回 'CACHED'  ← 不读 assets
  4. 都没有                → 返回 'NEED'

原生侧按返回值：
  'NEED'   → 读一次 assets/js/eruda.js
             → evaluateJavascript("localStorage.setItem('__laogua_eruda_js', <JSON 字面量>)")
  'CACHED' / 'NEED' 都继续 → eruda.init({useShadowDom:true, defaultPanel:'console'})
                             + console.config.set('displayTimestamps', true)
```

要点：
- localStorage 键名：`__laogua_eruda_js`（常量 `ERUDA_LS_KEY`）。
- **474KB 脚本用 `org.json.JSONObject.quote(js)` 转义后当字符串参数传**，
  绝不手工拼转义 —— 本项目在「内嵌 JS 模板字符串」上已翻车多次
  （见记忆「内嵌模板字符串的 JS 必须做 vm.Script 语法自检」）。
- 474KB 走 `evaluateJavascript` 是安全的：Chromium 的 devtools 通道按块传，
  不是 Binder 单包上限（之前担心的 Binder 问题不适用）。
- 新增 `readAsset()`（返回 `String?`，读不到不影响 H5）。

## 三、附带验证的接线（重要，否则白做）

`PkJsInjector.injectIfEnabled()` **确实**在 `PkH5Screen` 的 `onPageFinished` 里被调用
（`PkH5Screen.kt:239`），`markPageStarted` 在 `onPageStarted`（:216）。
